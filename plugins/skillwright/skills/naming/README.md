# naming

[Skill instructions](SKILL.md) · [Evaluation cases](../../evals/naming/README.md)

Choose a name by the job it needs to do. Ask for a product name, a service label, a project rename, a document naming scheme, or a comparison of existing candidates. Supply the audience, normal channel, constraints, and existing conventions when available.

The result is a brief, a meaningful shortlist or comparison, a recommendation with costs, and unresolved checks. A quick comparison can be short. Actual trademark clearance and audience testing remain separate work unless those checks are performed with appropriate resources.

## Design record

| Decision | Rationale |
|---|---|
| Case | ② for “naming”: select names for user-facing objects, rather than code refactoring or personal naming. The combined judgement has no single borrowed protocol; criteria use familiar concepts such as task success, hard constraints, and migration cost. |
| Side effect removed | Attractive word lists and persuasive origin stories can displace the decision about actual use. |
| Output form pinned | Brief, differentiated candidates or supplied shortlist, recommendation and tradeoffs, outstanding checks. Scale the form to the request. |
| Trigger width | Model-invocable for explicit naming requests. False triggers during routine implementation cost more than missing an incidental naming opportunity. Route code refactoring to implementation. |

## Criterion provenance

The failure descriptions below define testable risks, not claims that each failure has been observed on a particular model.

| Criterion | Failure it targets |
|---|---|
| Primary use and information allocation | A poetic internal label obscures the action at a public service entrance. |
| Different semantic directions | A list appears diverse but only substitutes synonyms within one image. |
| Binding constraints before preference | A favoured story wins despite a known input or comprehension barrier. |
| Origin versus creative association | A supplied fictional classical origin is repeated as fact. |
| Separate metrics and performed checks | Simulated users are presented as research, or domain availability as trademark clearance. |
| Expansion and migration cost | A renamed series breaks its existing distinction or discards valuable recognition without accounting for it. |

## How to judge the result

A reader can explain why the recommendation fits the intended use, what would disqualify it, and which evidence could change the choice. No test result, origin story, or availability claim is invented. A short user request does not automatically require a long report.

The skill fails if every option is the same metaphor, the story repairs a basic usability failure, or an untested recommendation is described as proven best.
